# Codex review: kit additions, round 1

Scope: `090db35..6e058ac`. All source locations below refer to `6e058ac`. I made no source edits, commits or stashes. Other working-tree changes appeared during the review; this report does not review those changes.

1. **should-fix** - `web/src/kit/Checkbox.tsx:30` and `web/src/kit/Radio.tsx:34`: the explanatory note becomes both part of the accessible name and the accessible description. The enclosing `<label>` contains the note, and `aria-describedby` references that same note again. On `/kit`, Chrome's accessibility tree reports the first radio's name as "Ask first Issues wait on Intake until someone takes them in." and its description as "Issues wait on Intake until someone takes them in." The checkbox has the same duplication. Screen readers using both properties repeat the explanation whenever a choice receives focus. Give the label text its own id and name the control from that text alone; retain the note only as its description, while preserving the whole row as a click target.

2. **should-fix** - `web/src/kit/Checkbox.tsx:24`: Checkbox ignores the FormRow description and validity context. Rendering it inside `<FormRow label="Checkbox row" note="Row note" problem="Choose a value">` produces a focusable checkbox with neither `aria-invalid` nor a reference to the row's note or problem. Unlike Toggle, Radio and the other form controls, it loses the error explanation when reached directly by keyboard or assistive technology. Consume `useDescribed()` and combine the row's description ids with the checkbox's own optional note instead of replacing either description.

3. **should-fix** - `web/src/kit/Dialog.tsx:180`, with `web/src/kit/toast.tsx:45`: a dialog's toast region remains interactive outside its modal confirmation question. Full makes only its `.frame` inert when `ask` is present; the new toast portal mounts directly in the native dialog, alongside that frame and the question. Reproduced with an in-memory composition of the existing components: raise a toast inside a full Dialog, show its `ask`, then press F6 from the question's first action. Focus moves to the Notifications region outside the `aria-modal="true"` alertdialog, and the toast's controls remain available. Suspend or make the toast region and its focus guards inert while the question is active, including preventing its global F6 handler from moving focus out of the question. Restore normal toast access after dismissal.

4. **should-fix** - `web/src/features/shared/TicketMenu.tsx:10`: the copy failure handler does not cover an unavailable Clipboard API. On an ordinary HTTP origin, Chrome exposes no `navigator.clipboard`; both copy actions throw synchronously before `.then()` is reached, so the person gets no copy and no failure toast. Reproduced with the fixture app served through intercepted local requests at `http://review.invalid/t/NW-17`: `isSecureContext` was false, `navigator.clipboard` was undefined, and Copy key raised "Cannot read properties of undefined (reading 'writeText')" while Notifications stayed empty. Check clipboard availability at this browser boundary and route that case through the existing failure feedback, or provide a supported copy fallback.
